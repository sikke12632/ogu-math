## 1. 문제 생성기

### 1.1 인터페이스 계약

```ts
generateSet(seed: string, config: SetConfig): Problem[]
```

- **입력**: `seed` (세션 ID 문자열), `config` = `{ unit: '5-2-1', counts: {easy:4, mid:3, hard:2} }`
- **출력**: `Problem[]` — 요청한 난이도 구성에 정확히 맞는 배열. 같은 seed면 항상 같은 결과(재현성)
- **실패**: 가드 조건을 만족하는 수치를 50회 내에 못 뽑으면 해당 템플릿을 건너뛰고 같은 난이도의 다른 템플릿으로 대체. 그래도 못 채우면 에러를 던지고 세션 시작을 막는다 — 조용히 문항 수를 줄이면 안 된다.

```ts
type Problem = {
  id: string
  templateId: string          // 'T1' ~ 'T7'
  params: Record<string, string>   // 어떤 변주로 생성됐는지
  difficulty: 1 | 2 | 3
  points: number              // 1 | 2 | 3
  prompt: string
  visual?: Visual             // 그림이 필요한 문항만 — 판별 유니온(확장 대비)
  choices?: string[]          // 없으면 단답 입력형
  answer: string | string[]
  explanation: string         // 필수. 게임 후 해설에 사용
}

// 처음부터 판별 유니온으로 둔다. 5-2-1은 numberline만 쓰지만,
// 3단원(합동과 대칭)·5단원(직육면체)은 도형이 필요하다.
// 여기서 NumberLineSpec으로 못박으면 나중에 전면 수정이 된다. (아키텍처 설계서 9.2)
type Visual =
  | { kind: 'numberline'; spec: NumberLineSpec }
  | { kind: 'fraction'; spec: FractionSpec }      // 2·4단원
  | { kind: 'figure';   spec: FigureSpec }        // 3·5단원
  | { kind: 'table';    spec: TableSpec }         // 6단원

type NumberLineSpec = {
  min: number; max: number; step: number
  marks: { at: number; type: 'filled' | 'hollow' }[]   // ● 포함 / ○ 미포함
  ray?: 'left' | 'right' | 'both'
}
```

`explanation`을 **필수 필드**로 둔 이유: 게임이 끝나고 교사 화면에 틀린 문항을 띄워 짚어주는 게 이 수업의 마무리다. 나중에 붙이려면 템플릿을 전부 다시 열어야 한다.

### 1.2 템플릿 카탈로그 — 7개

초등 수학은 단원 내 문항 유형이 애초에 많지 않고, 단원 간 혼합도 없다. 대부분은 **같은 사고를 요구하면서 숫자와 지시만 다른** 문항이다. 따라서 템플릿을 늘리는 대신, **진짜로 다른 사고를 요구하는 7개**로 압축하고 나머지 변주는 전부 파라미터로 처리한다. 아래 목록은 교과서 워크북·시중 문제집·평가 자료의 **출제 유형을 조사해 검증한 결과**다(유형은 아이디어이므로 조사 대상이며, 문항 자체는 복제하지 않고 직접 설계한다).

| ID | 유형 | 요구하는 사고 | 성취기준 |
|---|---|---|---|
| **T1** | 범위 판별 | 용어 → 해당 여부 판정 | 6수01-02 |
| **T2** | 수직선 ↔ 범위 | 시각 표현과 언어 표현의 변환 | 6수01-02 |
| **T3** | 범위 안 개수 세기 | 경계 포함 여부 판단 | 6수01-02 |
| **T4** | 어림하기 | 자리 판정 | 6수01-03 |
| **T5** | 어림 역방향 | 결과 → 원래 수의 범위 (범위 + 어림 결합) | 6수01-02·03 |
| **T6** | 방법 선택 + 적용 | 맥락에 맞는 방법 판단 → 값 산출 | 6수01-03 |
| **T7** | 어림 방법 간 결과 비교 | 세 방법의 결과가 같아지는 조건 이해 | 6수01-03 |

> **T5가 이 단원의 핵심 문항이다.** 범위와 어림을 연결하는 유일한 유형이고, 교과서가 둘을 한 단원으로 묶은 이유이기도 하다. 상 난이도에 반드시 1문항 이상 포함시킨다.

**통합한 것들**: "용어 판별"과 "실생활 판정"은 껍데기만 다른 같은 구조여서 T1로 합쳤다(`context` 파라미터). "자연수 어림"과 "소수 어림"은 판단 과정이 동일하므로 T4로 합쳤다(`numberType` 파라미터).

**유형 조사 결과 되살린 것 (T7)**: 초기 안에서는 "세 방법 비교"를 T4의 반복으로 보고 제외했으나, 실제 출제 자료를 조사한 결과 **교과서 워크북·문제집 양쪽에서 빈번하게 등장**한다. 그리고 사고가 실제로 다르다 — T4는 어림을 *실행*하는 것이고, T7은 **"어떤 수일 때 올림과 반올림 결과가 같아지는가"**를 이해해야 풀린다. 가드 G1(어림 자리 아래 첫 자리 0 금지)이 존재하는 이유와 같은 개념이므로, 이 유형을 빼면 학생이 그 원리를 만날 기회가 사라진다. 상 난이도로 편성한다.

**T6 범위 확장**: 조사 결과 실제 문항은 "어떤 방법을 쓸까"에서 끝나지 않고 **"그래서 몇 개/몇 대인가"까지 묻는다**(버스 최소 대수, 포장 최대 개수, 필요한 금액). 방법 선택만 묻는 형태와 값까지 묻는 형태를 `ask` 파라미터로 나눈다.

### 1.3 파라미터 — 변주는 여기서 만든다

템플릿 6개에 파라미터를 곱하면 수십 가지 문항이 나온다. 여기에 수치 랜덤이 더해지므로 **같은 문제가 반복된다는 느낌은 생기지 않는다.**

| 템플릿 | 파라미터 | 값 |
|---|---|---|
| T1 | `term` / `context` / `format` | 이상·이하·초과·미만 / 순수·키·요금·인원·무게 / 다중선택·OX |
| T2 | `direction` / `boundary` | 수직선→말·말→수직선 / 한쪽·양쪽 |
| T3 | `numberType` / `bounds` / `extra` | 자연수·소수 / 한쪽 열림·양쪽 닫힘 / 없음·홀짝·배수·두 범위 교집합·미지수 역산 |
| T4 | `method` / `numberType` / `place` / `format` | 올림·버림·반올림 / 자연수·소수 / 십·백·천·소수 첫째·둘째 / 선택형·단답형 |
| T5 | `method` / `numberType` / `place` | 위와 동일 |
| T6 | `scenario` / `ask` / `post` | 버스 대수(올림)·상자 포장(버림)·물건값 지불(올림)·인구 추산(반올림)·판매 가능 수량(버림) / 방법만·값까지 / 없음·나머지·묶음수×단가·합산후어림 |
| T7 | `pair` / `format` | 올림↔반올림·버림↔반올림·세 방법 전부 / 같은 것 고르기·다른 것 고르기 |

**난이도는 템플릿이 아니라 파라미터가 결정한다.**

| 난이도 | 조건 | 요구 사고 |
|---|---|---|
| **하** | 용어·개념을 그대로 적용. 자연수, 세 자리 이하, 선택형 | 이해력 |
| **중** | 소수 또는 네 자리 이상 / 단답형 / 부가조건 1개(홀짝·배수·교집합) / 역방향 | 추론력 |
| **상** | **실생활 맥락 + 2단계** — 어림한 뒤 후처리 연산(나머지·묶음수×단가·합산 후 어림) | 문제해결력 |

**상 난이도의 정체는 "실생활 2단계"다.** 실제 심화 단원평가 두 회차를 분석한 결과, 상 난이도 10문항 중 8문항이 실생활 문제해결이었다(1.7 참조). 순수 계산을 어렵게 만드는 방향이 아니라, **맥락을 읽고 → 어림하고 → 한 번 더 연산하는** 구조가 난이도를 만든다.

발문이 길어지지만 계산 자체는 단순해서 **40~50초 안에 풀린다.** 오히려 "최댓값과 최솟값을 구해 합을 구하라" 같은 순수 수학형이 시간을 더 잡아먹는다.
### 1.4 가드 — 여기가 진짜 설계다

수치를 그냥 랜덤으로 뽑으면 **같은 템플릿인데 문제가 무의미해지거나 난이도가 폭발한다.** 대전 게임에서는 그게 곧 불공정으로 읽힌다. 템플릿마다 아래 가드를 건다.

| ID | 가드 | 이유 |
|---|---|---|
| **G1** | 어림 대상 자리 아래 첫 자리는 0 금지 | `340`을 십의 자리로 어림하면 올림·버림·반올림이 전부 340. 변별력 0 |
| **G2** | 반올림 기준 자리 숫자는 `{3,4,5,6,7}`에서 뽑되 `4`와 `5`가 40% 비중 | 경계값(4↔5)이 이 단원의 학습 목표. 랜덤이면 경계가 안 나온다 |
| **G3** | 연쇄 자리올림은 난이도 태그로 분리 | `2995 → 3000`은 자릿수가 바뀐다. 하 난이도에서 금지, 상 난이도에서 의도적 포함 |
| **G4** | 선택형 보기 4개의 값은 서로 달라야 함 | 오답 보기를 올림/버림 결과로 만들면 우연히 겹친다. 겹치면 재생성 |
| **G5** | 실생활 수치는 현실 범위로 클램프 | 키 100~150cm, 요금 100원 단위, 인원 1~40명. 안 걸면 "키 4823cm"가 나온다 |
| **G6** | 개수 세기 문항의 정답은 1~15개 | 그 이상은 세다가 시간이 다 간다 |
| **G7** | 한 세트 안에 같은 `templateId` 2회 초과 금지 | 9문항 중 5개가 T4면 세트가 아니다 |
| **G8** | T7에서는 G1을 **역으로** 적용 | T7은 "결과가 같아지는 수"를 다루므로 0으로 끝나는 수가 반드시 후보에 있어야 한다 |

### 1.5 세트 구성과 점수

| 난이도 | 문항 수 | 배점 | 소계 |
|---|---|---|---|
| 하 | 3 | 1점 | 3 |
| 중 | 4 | 2점 | 8 |
| 상 | 2 | 3점 | 6 |
| **계** | **9** | | **17점** |

9문항 / 8분 = 문항당 약 53초. 하 난이도를 앞에 배치해 초반 이탈을 막는다.

**성취기준 균형**: 범위(6수01-02) 5문항 : 어림(6수01-03) 4문항. 실제 단원평가가 범위 쪽에 약간 무게를 두는 것과 맞춘다(1.7).

**중 난이도를 두껍게 잡은 이유**: 시중 심화 단원평가는 하5:중10:상5로 중간이 절반이다. 하가 너무 많으면 변별이 안 되고, 상이 많으면 하위권이 초반에 포기한다.

### 1.7 난이도 캘리브레이션 근거 (실제 평가지 분석)

추측이 아니라 실제 평가 자료를 분석해 기준선을 잡았다.

**분석 대상**
- 에듀넷 티-클리어 차시 평가지 2종 (「올림과 버림 알아보기」, 「반올림 알아보기」, 각 10문항)
- 티셀파 5-2 1단원 **심화 단원평가 2회분** (각 20문항, 문항정보표 포함)

티셀파 자료에는 문항마다 **성취기준 · 평가영역 · 교과역량 · 난이도**가 태깅되어 있어 캘리브레이션 근거로 쓸 수 있었다.

#### 발견 1 — 난이도 분포는 5 : 10 : 5

두 회차 모두 하 5, 중 10, 상 5로 동일했다. **중간이 절반**이다. 초기 안(하4:중3:상2)은 하가 지나치게 많았다.

#### 발견 2 — 난이도는 "평가영역"과 강하게 연동된다

| 난이도 | 지배적 평가영역 |
|---|---|
| 하 | 이해력 |
| 중 | 추론력 |
| 상 | **문제해결력** (2회분 상 10문항 중 8문항) |

상 난이도가 전부 **실생활 활용**이었다. 계산을 어렵게 만드는 게 아니라 맥락을 얹는 것이 난이도를 만든다.

#### 발견 3 — 상 난이도 실생활 문항의 공통 구조 = **어림 + 후처리 연산**

관찰된 패턴:
- 두 값을 합산한 뒤 어림 (남학생 수 + 여학생 수 → 묶음 단위로 올림)
- 어림한 뒤 **나머지**를 구함 (쿠키를 상자에 담고 남는 개수)
- 어림한 뒤 **개수 × 단가** (포장지 묶음 수 × 묶음 가격, 꽃다발 수 × 가격)
- 도형 둘레를 계산한 뒤 어림

**어림 결과가 최종 답이 아니라 중간 계산인 구조**가 핵심이다. T6에 `post` 파라미터를 추가한 근거다.

#### 발견 4 — 범위(6수01-02) 문항이 어림(6수01-03)보다 많다

1회 12:8, 2회 10:10. **범위 쪽이 같거나 많다.** 초기 템플릿 구성은 범위 3개(T1~T3) 대 어림 4개(T4~T7)로 어림에 기울어 있었으므로, 세트 구성에서 범위 5 : 어림 4로 보정한다.

#### 발견 5 — T3(개수 세기)를 넓혀야 한다

실제 문항에서는 단순 개수 세기가 거의 없고 **부가조건이 붙는다**:
- 범위 안에서 홀수만 / 특정 수의 배수만 세기
- 두 범위의 **교집합**에 속하는 자연수 개수
- 포함되는 자연수가 N개일 때 **경곗값을 역산**
- 범위별로 분류해 각 구간의 개수를 세기

T3의 `extra` 파라미터로 흡수한다.

#### 발견 6 — 표(table)가 1단원에서도 필요하다

습도표, 나이표, 놀이기구 탑승 기준표, 영수증, 기록표 등 **표를 읽는 문항이 다수**였다. `Visual` 유니온의 `table`을 6단원용으로 미뤄 두었으나, **1단원에서 바로 구현해야 한다.** STEP 3 범위에 포함시킨다.

#### 우리 앱에 맞춘 조정

시중 평가지를 그대로 옮기지 않는다. 우리 쪽 제약이 다르다.

| 제약 | 조정 |
|---|---|
| 문항당 40~50초 | 발문을 2줄 이내로 압축. 표는 5행 이내 |
| 반 전원이 푼다 (심화반이 아님) | 티셀파 심화의 "하"는 우리 기준 "중"에 가깝다. 한 칸씩 내려서 캘리브레이션 |
| 게임 전 워밍업 성격 | 순수 수학형 다단계(최댓값·최솟값 구해 합 구하기)는 시간을 많이 먹으므로 상 2문항 중 최대 1개 |
| 자동 채점 | 서술형 불가. 선택형·단답형으로 변환 |

> **저작권**: 위 자료는 **유형·난이도 분포·발문 구조를 분석**하는 데만 사용했다. 문항 자체는 복제하지 않으며, 템플릿은 성취기준과 분석 결과를 근거로 새로 작성한다.

### 1.8 같은 문제 · 다른 순서

- 문제 세트는 **반 전체가 동일**하게 받는다 (`seed = sessionId`). 공정성 + 게임 후 다 같이 해설하기 위해.
- 단, **보기 순서는 학생마다 셔플**한다 (`seed = sessionId + studentId`). 옆자리 답 베끼기를 이걸로 막는다.

## 2. 시스템

### 2.1 세션 흐름

```
[교사] 세션 생성 → 6자리 코드 발급
   ↓
[학생] 접속 → 반 명단에서 이름 선택 → 대기실
   ↓
[교사] 인원 확인 후 "시작"          ← phase: waiting → quiz
   ↓
[전원] 문제 풀이 (교사 설정 5~10분)
   ↓  타이머 종료 또는 전원 제출
[시스템] 자동 채점 → 팀 배분 → 스탯 산출   ← phase: quiz → teaming
   ↓
[전원] 팀 게임 (5~10분)              ← phase: teaming → game
   ↓
[교사] 결과 + 오답 해설 화면 투영      ← phase: game → review
```

### 2.2 데이터 모델 (Firebase RTDB)

```
sessions/{sessionId}
  meta:    { code, unit, phase, startedAt, quizSeconds, gameSeconds }
  roster/{studentId}:  { name, joinedAt, connected }
  quiz/{studentId}:    { answers: {q1..q9}, submittedAt, score, percentile }
  teams/{teamId}:      { members: [studentId], avgScore, ap }
  game:    { board, turn, log }
```

### 2.3 상태 전이는 한 곳에서만

**`phase`를 바꿀 수 있는 건 교사 클라이언트뿐이다.** 학생 클라이언트는 읽기만 한다.

오구 운영센터의 기록 유실이 period-boundary 문제였던 것과 같은 계열의 함정이다. 상태 전이 주체가 여럿이면, 두 클라이언트가 시계가 1초 다른 것만으로 서로 다른 phase를 쓰고 데이터가 덮인다. 타이머도 각자 세지 말고 `meta.startedAt`에서 계산해 표시만 한다.

### 2.4 답안 저장 — 유실 방지

교실에서 반드시 일어나는 일: 새로고침, 앱 전환, 와이파이 끊김, 배터리 방전.

- 답 선택 즉시 `useState` 반영 → **500ms 디바운스** 후 RTDB write
- 동시에 `localStorage`에 미러링. 재접속 시 서버 값과 비교해 **최신 것 채택**
- **제출은 별도 플래그**. 미제출자도 마감 시점까지 저장된 답으로 채점된다 (마감 30초 전 예고 알림)
- `onDisconnect()`는 **접속 상태만** 관리한다. 답안 노드에 절대 걸지 말 것 — 끊기는 순간 답이 지워진다

### 2.5 네트워크 장애 대비

- 문제 세트 **전체를 세션 시작 시 한 번에** 내려받는다. 풀이 중에는 네트워크가 죽어도 계속 풀 수 있다
- 끊기면 로컬로 진행하고, 복구되면 일괄 동기화. 화면에는 작은 배지로만 표시(불안 유발 금지)
- 교사 화면에 **수동 진행 버튼**. 자동 전이가 실패해도 수업이 멈추지 않게
- 최악의 경우 오프라인 개인 연습 모드로 강등

### 2.6 규모

25명 × 9문항 × 디바운스 write ≈ 세션당 400~600 write. RTDB 무료 티어(동시접속 100, 월 10GB 전송)로 여유롭다. 유료 전환 불필요.

## 3. 게임

### 3.0 용어 고정

혼용을 막기 위해 세 층위를 분리한다.

| 용어 | 뜻 | 길이 |
|---|---|---|
| **턴** | 카드를 한 번 뽑는 단위 | 초 단위 |
| **판** | 1대1 승부 하나 | 30~40초 |
| **세션** | 게임 시간 전체 = 3판 | 5분 |

### 3.1 종목 결정: 1대1 카드 뽑기 대전

**푸시 유어 럭 + 불완전 정보** 구조. 구조적으로는 블랙잭과 홀덤의 교배종이되, 카지노 기표(21·딜러·히트/스탠드·카드 문양)는 일절 쓰지 않는다. 학부모 눈에 카지노로 읽히는 순간 메커니즘의 정당성과 무관하게 문제가 된다.

**전략 게임을 버린 이유**: 초기 안이었던 영토 확장전은 ① 팀 조작이 하나라 목소리 큰 학생이 독점하고 ② 턴 대기가 발생하며 ③ 반의 상당수가 "머리 쓰는 게임"에 붙지 않는다. 셋 다 밸런싱으로 해결되지 않는 구조적 결함이다.

**이 게임이 만족하는 조건**
- 룰 설명 20초 — "숫자 뽑아서 점수 쌓아, 꽝 뽑으면 짐, 언제든 멈출 수 있어"
- 판단은 "한 번 더? 그만?" 하나뿐. 계산이 아니라 배짱의 영역
- 실력이 개입할 여지가 거의 없어 **문제를 잘 푼 학생이 유리하지 않다**
- 깊이는 선택적 — 감으로 해도 성립하고, 확률을 세면 더 잘한다

### 3.2 판 규칙

**카드 풀 14장 = 숫자 1~12 (각 1장) + 꽝 2장**

1. **히든**: 판 시작 시 각자 1장을 **비공개**로 받는다. 히든에는 꽝이 들어가지 않는다
2. 매 턴 양쪽이 동시에 **"뽑기 / 스탑"** 을 선택 → 동시에 공개
3. **스탑은 영구**. 한 번 접으면 그 판에서 다시 뽑을 수 없다
4. **꽝을 뽑으면 그 즉시 패배** (점수 비교 없음)
5. **꽝 2장은 1턴 종료 후 풀에 투입**된다 — 첫 턴은 안전
6. 양쪽 스탑 또는 결착 시 **히든 공개 후 합산**, 높은 쪽 승. 동점·동시 꽝은 무승부

### 3.3 확률 곡선

히든 2장이 먼저 빠지고, 매 턴 양쪽이 1장씩 = 2장이 소비된다. 분모는 줄고 분자는 고정이라 위험이 가속한다.

| 턴 | 남은 카드 | 꽝 | 내가 죽을 확률 | 이 턴에 판이 끝날 확률 |
|---|---|---|---|---|
| 1 | 10 | 0 | **0%** | 0% |
| 2 | 10 | 2 | 20% | 38% |
| 3 | 8 | 2 | 25% | 46% |
| 4 | 6 | 2 | 33% | 60% |
| 5 | 4 | 2 | 50% | 83% |
| 6 | 2 | 2 | 100% | 100% |

**5턴까지 갈 수 있는 구조이고, 6턴은 반드시 끝난다.** 판 하나는 40~50초, 3판에 결과 화면을 더해 5분에 들어맞는다.

> **다만 매 판이 5턴까지 가지는 않는다.** 계산하면 5턴 도달률은 **13%** 다. 평균적으로는 3~4턴에 끝나고, 5턴은 일곱 판에 한 번쯤 나오는 "끝까지 간 판"이 된다. 이건 결함이 아니라 오히려 쓸 만한 성질이다 — 매번 5턴이면 긴장이 평준화되고, 가끔 나오니까 그 판이 사건이 된다.
>
> 5턴 도달률을 더 올리고 싶다면 레버는 하나뿐이다: **꽝을 1장으로 줄이기**(도달률 13% → **33%**). 대신 매 턴 위험이 절반이 되어 스탑 판단이 헐거워진다. 프로토타입에서 양쪽을 다 돌려보고 정한다.
>
> **스탑이 판을 늘린다는 점도 계산에 넣어야 한다.** 한쪽이 스탑하면 턴당 카드 소비가 2장에서 1장으로 줄어 풀이 천천히 마른다. 위 도달률은 "둘 다 끝까지 뽑는" 최악의 경우이고, 실제로는 스탑이 섞여 5턴 이상 가는 판이 더 자주 나온다.

> **꽝을 매 턴 1장씩 추가하는 안은 기각.** 초반 위험이 6%대라 고민 없는 턴이 두세 개 생기고, 꽝 개수가 매 턴 변하면 학생이 추적할 수 없다. 고정 2장이면 "남은 카드 몇 장 중 2장"만 보면 되고, 첫 턴부터 판단이 진짜 판단이 된다.

### 3.4 히든이 하는 일

히든 1장이 이 게임의 핵심 장치다. 없으면 꽝 개수가 고정이라 **눈치 빠른 학생이 최적해를 기계적으로 계산**할 수 있고, 게임이 산수 문제로 전락한다.

히든이 있으면 **확률은 계산되지만 승패는 계산되지 않는다.** 상대 공개 점수가 앞서 보여도 내 히든이 크면 실제로는 내가 앞선다. 그래서 앞선 쪽도 스탑을 편하게 못 하고, 뒤처진 쪽에는 블러핑이라는 무기가 생긴다(이른 스탑은 "히든이 크다"는 신호로 읽힌다).

**층위가 셋으로 갈린다** — 감으로 하는 학생 / 꽝 확률만 보는 학생 / 남은 숫자까지 세는 학생. 셋이 같은 게임을 하되 아래 층이 위 층에 압도당하지 않는다. 히든이 불확실성을 유지해 주기 때문이다.

### 3.5 화면 정보 설계

**항상 표시**
```
나 27   ·   상대 19 + ?
내가 뽑은 카드:  8  4  11
남은 카드 6장    그중 꽝 2장   [■■□□□□]
```

- **`+ ?`** — 상대 점수가 불완전 정보임을 계속 상기시킨다. 계산은 대신 해주지 않는다
- **꽝 비율 게이지** — 숫자를 안 읽는 학생도 "빨간 게 늘었다"로 위험을 파악한다. 숫자를 읽는 학생과 같은 판단에 도달할 수 있게 하는 장치
- **내 카드 이력은 표시한다.** 카운팅의 재미는 상대 히든 추론에 있지 자기 카드 암기에 있지 않다
- **상대가 스탑했다는 표시는 크게.** 가장 중요한 정보인데 숫자가 아니다

**표시하지 않음**
- **"아직 안 나온 숫자" 목록** — 계산을 대신 해주는 UI다. 카운팅이 실력이 되려면 게임이 떠먹여주면 안 된다

숫자를 1~12로 고정한 이유가 여기 있다. 합이 78이므로 `78 − (내 카드 합) − (상대 공개 합)` 이 곧 **상대 히든 + 미공개 카드의 합**이다. 턴이 진행될수록 이 덩어리가 줄어 상대 히든 후보가 좁혀진다. 5학년이 머리로 하기에 딱 맞는 난이도이며, 6학년 2학기 '가능성' 단원으로 그대로 확장할 수 있다.

### 3.6 팀 배분

1. 점수 내림차순 정렬
2. **상·중·하 3구간**으로 나눈 뒤 **구간 내에서 셔플**
3. 셔플된 순서로 **스네이크 드래프트** (1-2-3-4 / 4-3-2-1 / …)

2단계를 넣는 이유: 순수 점수순 스네이크를 몇 주 돌리면 학생들이 팀 구성만 보고 서열을 역산한다. 구간 내 셔플이면 팀 균형은 유지되면서 개인 순위는 흐려진다.

**점수의 역할은 여기서 끝난다.** 게임 안에서 점수는 어떤 어드밴티지도 주지 않는다.

### 3.7 매칭

- **매 판 새로 매칭**한다. 상대 팀 구성원 중 **랜덤**
- 3판 결과는 **누적**. 팀별 승수 합계로 승부

**같은 상대와 3판을 붙이지 않는 이유**: 매칭이 고정되면 홀수 인원일 때 한 명이 세션 내내 논다. 매 판 교체하면 쉬는 사람이 판마다 바뀌어 부담이 1/3로 준다. 덤으로 상대 스타일이 학습되지 않아 덜 질린다.

**실력별 매칭(상중하 그룹 내 대전)은 채택하지 않는다.** 팀 배분에서 이미 실력을 섞었으므로 이중 보정이며, 매번 비슷한 상대와 붙으면 서열이 다시 드러난다.

**개인 전적이 3:0으로 갈려도 무방하다.** 12쌍이 동시에 돌아가므로 팀 합계에서 상쇄된다. 오히려 전원이 2:1이면 팀 점수가 평준화되어 결과가 밋밋해진다. 다만 결과 화면은 **팀 성적을 크게, 개인 전적을 작게** 배치한다.

### 3.8 홀수 인원 — 응원단장

인원이 홀수면 매 판 한 명이 상대 없이 남는다. 이 학생은 그 판 동안 **응원단장**이 된다. 부전승 처리보다 낫다 — 쉬는 게 아니라 역할이 생기기 때문이다.

응원단장 화면에서 할 수 있는 것:
- 우리 팀 매치 현황 실시간 관전 (**점수만**, 카드는 보이지 않음 — 훈수 방지)
- **응원 보내기**: 팀원을 골라 버튼을 누르면 그 학생 화면에 잠깐 표시된다
- 판 종료 후 우리 팀 **MVP 지목**

응원 버튼이 핵심이다. 손이 움직이고 자기가 무언가 하고 있다는 감각이 있어야 이탈하지 않는다.

역할은 판마다 로테이션한다. 3판이면 최대 3명이 각 1판씩 맡는다.

### 3.9 연결 끊김

이 게임은 상대가 있어야 진행되므로, 한 명이 튕기면 상대까지 멈춘다. 대기 시간 0으로 설계한 구조가 여기서 무너지므로 반드시 처리한다.

- **10초 무연결 → 튕김 확정, 해당 판 패배.** 상대는 즉시 승리 처리되고 다음 판으로 넘어간다. 기다리지 않는다
- **다음 판 매칭 전에 복귀하면 매칭 풀에 다시 넣는다.** 세션에서 배제하지 않는다
- 화면에는 "상대 연결 확인 중" 정도로만 표시하고 카운트다운을 크게 띄우지 않는다

### 3.10 왜 이 구조가 하위권을 죽이지 않나

점수를 개인 어드밴티지로 주면 잘하는 학생이 문제에서 이기고 게임에서 또 이긴다. 하루에 두 번 지는 구조이며, 게임을 붙인 이유(참여율)와 정면으로 충돌한다.

이 설계에서는 점수가 **팀 배분에만** 쓰이고 게임 안에서는 아무 힘이 없다. 게임 자체가 운 기반이라 누구나 승률 50%이고, 3판을 서로 다른 상대와 붙으므로 한 판 말려도 만회할 수 있다. 결과는 팀 단위로 집계되어 개인의 패배가 노출되지 않는다.

## 4. 기술 스택

| 영역 | 선택 | 근거 |
|---|---|---|
| 프레임워크 | **Vite + React + TypeScript** | 단일 HTML로는 상태 관리가 감당 안 되는 규모. 배포는 `firebase deploy` 한 줄 |
| 실시간 | **Firebase RTDB + Anonymous Auth** | 학생 계정 안 만듦. 이름은 명단에서 선택만 |
| 게임 렌더 | **React + CSS 애니메이션** | 카드 뒤집기·게이지가 전부다. 게임 엔진이 붙는 순간 디버깅 난이도만 올라간다 |
| 배포 | Firebase Hosting | RTDB와 같은 프로젝트에서 관리 |
| 문제 생성기 | **독립 모듈** (`/src/generator`, Firebase 의존 0) | 게임이 엎어져도 문제 은행은 살아남게. 단독 실행·단독 테스트 가능 |

**기존 자산 재활용**: `ogu-modular-survivors`의 Phaser 코드는 장르가 달라 쓰지 않는다. 다만 확보해둔 **Ninja Adventure CC0 스프라이트는 팀 아이콘·응원 이펙트로 그대로 쓸 수 있다.**

**개인 기기 전제**: 공용 화면 없이 각자 기기에서 진행한다. 따라서 화면 하나에 필요한 정보가 다 들어가야 하고(3.5 참조), 세로 화면에서도 깨지지 않아야 한다.

## 5. 개발 순서

각 단계가 **그 자체로 수업에 쓸 수 있는 상태**로 끝나게 쪼갰다. 학기 중에 안전하게 굴리려면 이게 중요하다.

| 단계 | 산출물 | 수업 투입 가능 여부 |
|---|---|---|
| **0** | 문제 생성기 단독 + 100세트 덤프 | 인쇄해서 학습지로 사용 가능 |
| **1** | 로컬 퀴즈 앱 (Firebase 없음) | 개인 연습용으로 사용 가능 |
| **2** | 세션 + 대기실 + 동시 시작 + 채점 + 해설 화면 | **게임 없이 여기까지로 한 번 수업에 써본다** |
| **3** | 팀 배분 + 매칭 + 1대1 카드 대전 | 완성 형태 |
| **4** | 단원 확장 (5-2 2~6단원) | 학기 전체 |

**0단계에서 반드시 멈춰서 100세트를 눈으로 검수할 것.** 가드가 제대로 걸렸는지는 코드를 봐서는 모르고, 뽑힌 문제를 봐야 안다. 여기서 새는 걸 못 잡으면 3단계까지 가서 "게임은 되는데 문제가 이상하다"가 된다.

## 6. 열린 결정 사항

보고서 범위 밖이라 정하지 않은 것들 — 진행 전에 확정 필요:

1. **기기 종류**: 태블릿 / 크롬북 / 개인 스마트폰 → 화면 비율과 입력 방식이 UI를 바꾼다
2. **명단 관리**: 매번 이름 선택 vs 기기별 고정 매핑
3. **누적 기록**: 회차별 점수를 쌓아 성장 그래프를 보여줄 것인가 (개인정보·비교 노출 문제 있음)
4. **오답 재도전**: 게임 후 틀린 문제만 다시 푸는 판을 넣을 것인가
5. **게임 이름**: 카지노 기표를 피하는 이상 명칭도 중립적이어야 한다 (예: 탐험·수집 계열)
