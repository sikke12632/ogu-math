# 사이트 아키텍처 설계서

**전제 문서**: 「수학 퀴즈배틀 설계보고서」 — 문제 생성 원칙(1장), 데이터 신뢰성(2장), 게임 규칙(3장)
**이 문서의 범위**: 화면 구조 · 라우팅 · 상태 매트릭스 · 확장 구조 · 문제 은행 구축 방식
**작성일**: 2026-08-20

---

## 0. 요구사항 확인

작성자가 지시한 흐름을 그대로 옮기면:

```
담임: 단원 선택 → 게임 선택 → 세션 시작
  ↓
학생: 접속 → 문제 풀이(제한시간) → 미제출자 자동 마감
  ↓
채점 → 점수 안내 → 팀 배정
  ↓
팀 대결
  ↓
(사후) 학생이 자기 오답 확인
```

동시에 **전자칠판**에 입장 QR·대기 화면·팀 현황 등을 띄운다. 카훗과 같은 이원 화면 구조.

**이해한 대로라면 맞다.** 다만 아래 세 가지는 그대로 가면 문제가 생기므로 설계에서 바꿨다.

## 1. 먼저 짚을 세 가지

### 1.1 화면은 둘이 아니라 셋이어야 한다

카훗은 **호스트 화면 1 + 플레이어 화면 N** 구조다. 그런데 카훗의 호스트 화면은 곧 공용 화면이라, 교사가 조작하는 버튼과 학생들이 보는 정보가 한 화면에 있다.

교실 전자칠판은 **학생 전원이 보고 있다.** 여기에 교사 제어 버튼, 세션 코드 관리, 명단, 점수 원본이 함께 뜨면 안 된다. 그래서 화면을 셋으로 나눈다.

| 화면 | 기기 | 성격 |
|---|---|---|
| **교사 콘솔** | 교사 노트북·태블릿 | 제어. 학생에게 안 보임 |
| **보드 뷰** | 전자칠판 | 읽기 전용. 조작 불가, 민감 정보 없음 |
| **학생 뷰** | 개인 기기 | 자기 것만 |

보드 뷰는 **로그인 없이 URL만으로 열리는 읽기 전용 페이지**다. 전자칠판에 띄워 두고 잊어버려도 되게. 교사 PC가 전자칠판과 미러링된 환경이면 브라우저 창 두 개를 띄우면 된다.

### 1.2 전자칠판에 개인 점수를 띄우면 안 된다

카훗의 상징이 실시간 개인 리더보드인데, **이건 이 설계에서 의도적으로 버린다.**

앞선 논의에서 게임 규칙을 운 기반으로 잡고, 점수를 팀 배분에만 쓰고, 결과를 팀 단위로 집계한 이유가 전부 "하위권을 두 번 지게 하지 않는다"였다. 그렇게 공들여 놓고 마지막에 개인 등수를 교실 앞 대형 화면에 띄우면 그 설계가 통째로 무효가 된다.

**보드 뷰의 원칙**
- 개인 점수 · 개인 등수 · 개인 정답률 → **표시 금지**
- 팀 단위 집계, 진행 상황, 참여 현황 → 표시
- 문제 풀이 중 "누가 몇 개 맞았는지" → 표시 금지. **제출 인원수만** (12/25)

개인 점수는 **자기 기기에서만** 본다.

### 1.3 문제는 "수집"이 아니라 "설계"여야 한다

인터넷에서 문항 30개를 모아 코드에 넣는 방식은 두 가지 문제가 있다.

**하나, 저작권.** 교과서·문제집·학습지 문항은 저작물이다. 숫자만 바꿔도 문항 구조와 표현을 그대로 가져오면 복제에 해당한다. 교내 수업 목적의 인용은 폭이 넓지만, 앱에 30개를 상시 내장하는 건 인용이 아니라 데이터베이스 구축이다.

**둘, 품질이 안 올라간다.** 모아온 문항은 대개 "정답이 하나로 고정된 완성품"이라 수치를 랜덤화하면 오히려 깨진다. `340`을 뽑아 올림·버림·반올림 결과가 전부 같아지는 사고가 정확히 여기서 난다.

**대신 이렇게 한다.**
1. 시중 문항의 **유형만 조사**한다 (어떤 형식이 나오는가 — 이건 아이디어이지 저작물이 아니다)
2. 성취기준 [6수01-02], [6수01-03]에 맞춰 **템플릿을 직접 작성**한다
3. 템플릿마다 가드를 걸어 랜덤화해도 깨지지 않게 만든다

**개수는 30개가 아니라 6개다.** 초등 수학은 단원 내 유형이 애초에 적고 단원 간 혼합도 없어서, 30개를 채우면 "T4의 자릿수만 다른 것" 같은 중복이 들어간다. 진짜로 다른 사고를 요구하는 7개로 압축하고 변주는 파라미터로 만든다(보고서 1.2~1.3). 유형 조사는 완료했고, 그 결과 초기 안에서 잘못 뺀 유형 하나(T7 어림 방법 간 결과 비교)를 되살렸다. 검수량이 3000문항에서 100문항 안쪽으로 줄어든다는 점이 결정적이다.

## 2. 화면별 상세

### 2.1 교사 콘솔

**세션 만들기 (3단계)**

```
1) 단원 선택      [5-2-1 수의 범위와 어림하기]  ← 현재 1개, 드롭다운
2) 게임 선택      [카드 뽑기 대전]              ← 현재 1개, 드롭다운
3) 세부 설정      풀이 시간 [8분]  문항 수 [9]
                  게임 판 수 [3판]
                  → [세션 시작]
```

단원·게임이 지금은 각 1개뿐이지만 **선택 UI를 처음부터 만든다.** 나중에 추가할 때 화면을 고칠 일이 없게.

**세션 중 콘솔**

| 요소 | 내용 |
|---|---|
| 현재 phase와 남은 시간 | 크게 |
| 접속 현황 | 명단 + 접속/미접속, 끊긴 학생 강조 |
| 제출 현황 | 실시간 n/25, 미제출자 이름 |
| **수동 제어** | `다음 단계로` `일시정지` `타이머 +2분` `이 학생 재접속 처리` |
| 채점 결과 | 문항별 정답률 (교사만 봄 — 어느 문제를 다시 설명할지 판단용) |

**수동 제어 버튼이 핵심이다.** 자동 전이가 실패해도 수업이 멈추면 안 된다. 특히 `다음 단계로`는 어떤 phase에서도 눌리게 한다.

### 2.2 보드 뷰 (전자칠판)

phase별로 화면이 통째로 바뀐다. 글자는 교실 뒤에서 읽히는 크기로.

| phase | 보드에 뜨는 것 |
|---|---|
| **lobby** | **QR 코드 대형** + 6자리 코드 + 접속 인원 카운터 + 들어온 이름이 하나씩 튀어나오는 연출 |
| **quiz** | 남은 시간(대형 타이머) + 제출 인원 `12 / 25` + 격려 문구. **점수·정답률 없음** |
| **grading** | 채점 중 애니메이션 (3~5초, 짧게) |
| **teaming** | **팀 배정 발표.** 팀별로 이름이 하나씩 배치되는 연출 — 이 순간이 하이라이트다 |
| **game** | 팀별 승수 실시간 + 진행 중인 매치 수 + 응원단장 이름. **개인 전적 없음** |
| **result** | 팀 순위 + 팀별 MVP + 다음 예고 |

**lobby 연출이 생각보다 중요하다.** 접속하는 데 걸리는 1~2분이 그냥 빈 시간이 되면 소란스러워진다. 이름이 뜨는 것만으로도 학생들이 화면을 본다.

### 2.3 학생 뷰

```
진입    →  세션 코드(QR로 자동 입력) → 명단에서 이름 선택 → 대기
풀이    →  문항 카드 1개씩, 하단에 진행바. 이전/다음 자유 이동
          제출 버튼. 마감 30초 전 알림
결과    →  내 점수 + 우리 팀 발표
게임    →  카드 대전 화면 (또는 응원단장 화면)
종료    →  우리 팀 결과(크게) + 내 전적(작게) + [내가 틀린 문제 보기]
```

명단에서 이름 선택 방식이라 **학생 계정·비밀번호가 없다.** 초등에서 로그인 관리는 그 자체로 수업 시간을 잡아먹는다.

### 2.4 오답 기록 조회

세션이 끝난 뒤에도 학생이 자기 기록을 볼 수 있어야 한다.

```
/review  →  이름 선택  →  날짜별 목록
              ↓
          그 회차의 문항 목록
          문항 / 내 답 / 정답 / 해설
```

기존 보고서에서 `Problem.explanation`을 필수 필드로 잡은 이유가 여기서 쓰인다.

**개인정보 최소화**: 저장하는 건 이름과 회차별 점수·답안뿐이다. 학번·생년월일·연락처를 넣지 않는다. 학년말 일괄 삭제 기능을 함께 만든다.

## 3. 라우팅

```
/                        교사 로그인
/teacher                 세션 만들기 (단원 → 게임 → 설정)
/teacher/s/:sessionId    교사 콘솔
/board/:code             보드 뷰  (로그인 불필요, 읽기 전용)
/play/:code              학생 진입 → 이름 선택 → 세션 진행
/review                  기록 조회 (이름 선택)
```

QR 코드는 `/play/:code`를 가리킨다. 학생은 카메라로 찍으면 코드 입력 없이 바로 이름 선택 화면으로 간다.

## 4. 상태 매트릭스

`phase`는 교사 콘솔만 변경한다(기존 보고서 2.3). 세 화면이 같은 `phase`를 구독하고 각자 다른 것을 그린다.

| phase | 교사 콘솔 | 보드 뷰 | 학생 뷰 |
|---|---|---|---|
| `lobby` | 접속 명단, 시작 버튼 | QR·코드·인원 | 이름 선택 → 대기 |
| `quiz` | 제출 현황, 타이머 제어 | 타이머, 제출 수 | 문제 풀이 |
| `grading` | 문항별 정답률 | 채점 애니메이션 | 채점 중 |
| `teaming` | 팀 구성 확인·수동 조정 | **팀 발표 연출** | 내 점수 + 우리 팀 |
| `game` | 매치 현황, 끊김 감지 | 팀 승수 | 카드 대전 / 응원단장 |
| `result` | 세션 요약, 종료 | 팀 순위·MVP | 팀 결과 + 내 전적 + 오답 보기 |

**`teaming`에서 교사가 팀을 수동 조정할 수 있어야 한다.** 자동 배분이 항상 옳지는 않다 — 같은 팀에 두면 안 되는 조합이 교실마다 있다. 자동 결과를 보여주고 드래그로 바꿀 수 있게 한다.

## 5. 확장 구조

"단원 설정 → 게임 설정"이 나중에 늘어나는 게 전제이므로, **둘을 플러그인으로 분리**한다. 이게 이 설계에서 가장 중요한 결정이다.

### 5.1 단원 모듈

```ts
// src/units/index.ts
registerUnit({
  id: '5-2-1',
  name: '수의 범위와 올림, 버림, 반올림',
  grade: 5, semester: 2, unit: 1,
  generate(seed, counts): Problem[]     // 인터페이스 고정
})
```

새 단원 추가 = `src/units/5-2-2.ts` 파일 하나 추가 + 레지스트리 한 줄. 다른 코드는 건드리지 않는다.

### 5.2 게임 모듈

```ts
// src/games/index.ts
registerGame({
  id: 'draw-duel',
  name: '카드 뽑기 대전',
  matchSize: 2,                      // 1대1
  rounds: 3,                         // 판 수
  Component: DrawDuel,               // 학생 화면
  BoardComponent: DrawDuelBoard,     // 보드 뷰 표시
  resolve(matchResults): TeamScore[] // 팀 점수 산출
})
```

게임이 지켜야 할 계약은 **입력은 팀 배정, 출력은 팀별 점수** 이것뿐이다. 그 사이는 게임 마음대로. 이러면 나중에 완전히 다른 장르(협력형, 릴레이형)를 붙여도 세션 흐름은 그대로다.

### 5.3 폴더 구조

```
src/
  units/          단원별 문제 생성기   ← Firebase 의존 0
    _types.ts     Problem, SetConfig
    _guards.ts    공용 가드 (G1~G7)
    5-2-1.ts
  games/          게임 모듈
    _types.ts
    draw-duel/
  session/        phase 머신, 팀 배분, 매칭
  screens/
    teacher/  board/  student/
  lib/            firebase, storage, qr
```

`units/`는 Firebase를 몰라야 한다. 단독으로 실행해서 문항을 뽑아볼 수 있어야 검수가 가능하다.

## 6. 문제 은행 구축

### 6.1 구성

**템플릿 7개 × 파라미터 조합 × 수치 랜덤.** 난이도는 템플릿이 아니라 파라미터가 결정한다(보고서 1.3).

반복 회피는 템플릿 개수가 아니라 **수치 랜덤**이 담당한다. 같은 T4라도 매번 다른 수가 나오므로 "또 그 문제"라는 느낌이 생기지 않는다.

### 6.2 "오류는 없게" — 의지가 아니라 장치로

랜덤 생성기의 오류는 눈으로 다 잡을 수 없다. 세 겹으로 막는다.

**① 독립 검산**
템플릿마다 정답을 **두 가지 방법으로** 계산해 일치를 확인한다. 예를 들어 반올림은 ⓐ 자리 숫자 판정 방식 ⓑ `Math.round(n/unit)*unit` 방식으로 각각 구해 비교한다. 불일치하면 그 문항을 버리고 재생성한다.

**② 자동 검사 (템플릿당 1000회 생성)**
- 가드 위반 0건인가 (G1~G7)
- 정답이 유일한가 — 선택지 중 정답 조건을 만족하는 게 정확히 하나인가
- 선택지 값 중복이 없는가
- 문장에 `undefined`, `NaN`, 빈칸이 없는가
- 정답 위치가 특정 번호에 쏠리지 않는가

**③ 골든 스냅샷**
고정 시드로 뽑은 100문항(템플릿·파라미터 조합을 고루 덮게)을 **사람이 눈으로 검수**하고 그 결과를 파일로 저장한다. 이후 코드를 고칠 때마다 같은 시드로 뽑아 스냅샷과 비교한다. 달라지면 의도한 변경인지 확인한다. 회귀를 이걸로 막는다.

**①②는 자동, ③은 수동이다. ③을 건너뛰면 안 된다.** 자동 검사는 "형식이 맞는가"를 보지 "문제가 말이 되는가"를 보지 못한다.

## 7. 개발 순서 (개정)

기존 보고서 5장을 이걸로 대체한다.

| 단계 | 산출물 | 수업 투입 |
|---|---|---|
| **0** | 단원 모듈 6템플릿 + 검증 3종 + 골든 스냅샷 | 인쇄해서 학습지로 사용 |
| **1** | 학생 뷰 단독 (Firebase 없음, 로컬 풀이·채점·오답 확인) | 개인 연습용 |
| **2** | 세션 3화면 + lobby/quiz/grading/result. **게임 없음** | **여기서 한 번 수업에 써본다** |
| **3** | 팀 배분 + 매칭 + 카드 대전 + 보드 연출 | 완성 형태 |
| **4** | 기록 조회 `/review` + 학년말 삭제 | 운영 형태 |
| **5** | 단원 추가 (5-2 2~6단원) | 학기 전체 |

**2단계가 분기점이다.** 게임 없이 "동시 접속해서 같은 문제 풀고 채점받기"만 되어도 수업에 쓸 수 있다. 여기까지 한 번 돌려보고 실제 교실에서 뭐가 깨지는지 본 다음에 3단계로 간다. 3단계를 먼저 만들면 게임 버그와 인프라 버그가 섞여서 원인을 못 찾는다.

## 9. 확장 로드맵

5장은 확장 **메커니즘**(레지스트리 인터페이스)을 정의했다. 이 장은 **무엇을 어떤 순서로 붙일지**를 정한다.

### 9.1 단원 확장 — 순서는 단원 번호가 아니라 랜덤화 적합도

5-2 여섯 단원은 이 앱 방식에 대한 궁합이 전혀 다르다. **1 → 2 → 3 순서로 붙이면 3단원에서 막힌다.**

| 단원 | 필요한 그림 | 수치 랜덤 적합도 | 추가 난이도 |
|---|---|---|---|
| 1. 수의 범위와 어림 | 수직선 | ★★★ | — (완료 기준) |
| 4. 소수의 곱셈 | 없음 | ★★★ | **가장 쉬움** |
| 2. 분수의 곱셈 | 분수 표기 | ★★★ | 낮음 |
| 6. 평균과 가능성 | 표·그래프 | ★★☆ | 중간 |
| 3. 합동과 대칭 | 도형 | ★☆☆ | **높음** |
| 5. 직육면체와 정육면체 | 3D·전개도 | ★☆☆ | **높음** |

**권장 순서: 1 → 4 → 2 → 6 → (3·5)**

- **4단원(소수의 곱셈)을 두 번째로.** 그림이 아예 없고 수치만 바꾸면 되므로, 단원 모듈 인터페이스가 진짜로 재사용 가능한지 검증하는 데 최적이다. 여기서 코드를 거의 안 고치고 붙으면 구조가 옳은 것이다
- **2단원(분수의 곱셈)**은 분수 렌더링만 추가하면 된다. 가드는 약분·대분수 처리 정도
- **6단원(평균과 가능성)**은 표 데이터를 랜덤 생성해야 해서 가드가 새로 필요하다(평균이 정수로 떨어지게, 극단값 방지)

**3·5단원은 이 방식이 잘 맞지 않는다.** 도형 문제는 수치를 바꾸는 게 아니라 도형 자체가 바뀌어야 하는데, 도형을 랜덤 생성하면 "이상하게 생긴 도형"이 나오고 검수가 불가능해진다.

> **대안**: 3·5단원은 **고정 도형 은행 + 발문 랜덤** 방식으로 간다. 도형 SVG를 20~30개 직접 그려 두고(또는 교사가 추가), 문항은 "이 중 합동인 것", "대칭축의 개수" 처럼 발문과 정답만 조합한다. 랜덤화 폭은 줄지만 품질이 보장된다. **이건 다른 생성 방식이므로 단원 모듈 인터페이스에 `mode: 'generated' | 'banked'` 를 처음부터 넣어 둔다.**

### 9.2 지금 반드시 처리할 것 — `Problem.visual` 타입

초기 안은 `visual?: NumberLineSpec` 이었다. **이대로 STEP 2를 진행하면 안 된다.**

1단원만 보면 문제가 없지만, 2단원은 분수, 3·5단원은 도형, 6단원은 표가 필요하다. 렌더러가 이 타입에 의존해 만들어진 뒤에 바꾸면 학생 뷰·오답 조회·검수 스크립트가 전부 영향을 받는다.

**STEP 2에서 판별 유니온으로 정의한다.**

```ts
type Visual =
  | { kind: 'numberline'; spec: NumberLineSpec }   // 1단원
  | { kind: 'fraction';   spec: FractionSpec }     // 2·4단원
  | { kind: 'figure';     spec: FigureSpec }       // 3·5단원
  | { kind: 'table';      spec: TableSpec }        // 6단원
```

1단원 시점에는 `numberline`만 구현하고 나머지는 타입만 선언해 둔다. 렌더러는 `kind`로 분기하는 구조로 짜므로, 나중에 분기 하나를 추가하는 것으로 끝난다. **비용은 지금 10분, 나중에 하면 하루다.**

### 9.3 단원 하나 추가에 드는 실제 작업

| 작업 | 소요 | 재사용 여부 |
|---|---|---|
| 템플릿 5~8개 설계 | 클로드 코드 세션 1회 | 구조만 재사용 |
| 가드 작성 | 위와 동시 | G1~G8 중 절반은 그대로 |
| 자동 검사 | **자동** | 스크립트 100% 재사용 |
| 눈으로 검수 | 20~30분 (사람) | — |
| 등록 | 1줄 | — |

**화면·세션·게임은 한 줄도 안 고친다.** 이게 레지스트리 구조를 택한 이유다. 단원 추가가 "파일 하나 + 등록 한 줄"이 아니게 되는 순간 구조가 잘못된 것이므로, 4단원을 붙일 때 이 조건이 지켜지는지 확인한다.

### 9.4 게임 확장

게임 모듈의 계약은 **입력은 팀 배정, 출력은 팀별 점수** 하나뿐이다. 다만 현재 세션 레이어가 **1대1 매칭을 전제**하고 있어서, 이것만 일반화해 두면 어떤 게임이든 붙는다.

**STEP 8에서 함께 처리할 것**: 게임 모듈이 `grouping` 을 선언하게 하고, 세션 레이어는 그에 맞춰 인원을 묶는다.

```ts
grouping: 'duel'        // 1대1 (카드 뽑기 대전)
        | 'freeforall'  // 개인 전체전
        | 'teamwise'    // 팀 단위 하나씩
        | 'coop'        // 반 전체 협력 (매칭 없음)
```

`grouping`이 `coop`이면 매칭·응원단장 로직이 통째로 건너뛰어진다. 이걸 안 해두면 협력형 게임을 붙일 때 세션 레이어를 뜯어야 한다.

**게임 후보** (붙이는 순서는 정하지 않음 — 반응 보고 결정)

| 후보 | grouping | 특징 | 구현 난이도 |
|---|---|---|---|
| 카드 뽑기 대전 | `duel` | 운 중심, 불완전 정보 | — (완료 기준) |
| 땅따먹기 | `duel` | 전략 중심 — 카드 대전에 질렸을 때 대안 | 중 |
| 릴레이 정답 | `teamwise` | 팀원이 순서대로 한 문제씩 | 낮음 |
| 반 전체 협력 | `coop` | 반이 하나의 목표를 함께 채움. 대전이 부담인 학생용 | 중 |

**협력형을 하나쯤 확보해 두는 게 좋다.** 대전 형식 자체를 불편해하는 학생이 있고, 그 경우 게임을 바꿔도 소용이 없다. 교사가 세션 만들 때 대전형/협력형을 고를 수 있으면 그 문제가 해결된다.

### 9.5 학년 확장

단원 모듈이 학년에 의존하지 않으므로 6학년·4학년도 같은 구조로 붙는다. 단원 ID를 `5-2-1` 형식으로 잡아둔 이유다.

다만 **교사 콘솔의 단원 선택 UI가 학년 단위로 접혀야** 목록이 길어져도 쓸 만하다. STEP 6에서 드롭다운을 2단(학년 → 단원)으로 만들어 둔다.

### 9.6 확장 시 지켜야 할 선

- **단원·게임 추가가 코어 코드 수정을 요구하면 그 자체가 설계 결함 신호다.** 그때는 추가를 멈추고 인터페이스를 고친다
- 단원을 늘리기 전에 **기존 단원을 실제 수업에서 2~3회 굴려 본다.** 안 쓰는 단원 여섯 개보다 잘 도는 단원 두 개가 낫다
- 게임은 **최대 3개까지.** 그 이상은 교사가 매번 고르는 것 자체가 부담이 된다

## 10. 열린 결정 사항

1. **기기 종류** — 태블릿/크롬북/개인 스마트폰. 세로 화면 지원 여부가 UI를 바꾼다
2. **QR 스캔 가능 여부** — 학교 기기에 카메라가 없으면 6자리 코드 입력이 주 경로가 된다
3. **명단 등록** — 세션마다 입력 vs 학기 초 1회 등록 후 재사용
4. **보드 뷰 표시 방식** — 교사 PC 미러링 vs 전자칠판 자체 브라우저
5. **게임 이름** — 카지노 기표를 피하는 이상 명칭도 중립적이어야 한다
